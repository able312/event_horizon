Why the Internal Notes save/sync bug happens

A junior-friendly walkthrough of the Overview page notes field: why the UI can lie about which event’s notes you’re editing, how that becomes silent data loss in SQLite — and how to structure controlled fields and forms (saved state vs draft state) without the “four sources of truth” wiring mess.

The risk in one sentence The textarea is an uncontrolled input. React seeds it once on mount, then stops updating it — but blur still writes whatever is on screen into whatever event is currently loaded. That can overwrite or wipe notes.

1. Where the code lives

Parent loads the event and wires save. Child owns the textarea. 

// OverviewWorkspaceSection.tsx
<InternalNotesCard
  defaultValue={eventDetails?.internalNotes ?? ""}
  onUpdate={handleUpdateInternalNotes}  // → updateEvent({ internalNotes })
/>

// InternalNotesCard.tsx
<textarea
  defaultValue={defaultValue}
  onBlur={(e) => handleUpdate(e.target.value)}
/>

2. Core React idea: controlled vs uncontrolled

Uncontrolled (what we have)

Use defaultValue. The browser owns the text after first paint. Changing the React prop later does not change what the user sees in the box.

Controlled (safer for sync)

Use value={...} plus onChange (or remount with a key). React always drives what appears, so when the event changes, the text changes too.

3. Bug A — wrong event overwrite (high risk)

1

Open Event A

Query loads. Card mounts with defaultValue = "Caterer prefers email".

2

Navigate to Event B

URL / React Query switch to B. Parent re-renders with defaultValue = "VIP seating". Client details card updates (it reads props each render). The notes textarea does not.

3

Screen lies

You still see Event A’s notes while the rest of the Overview shows Event B. Easy to miss.

4

Blur saves into Event B

onBlur reads the DOM value ("Caterer prefers email") and calls updateEvent for the current route id — Event B. SQLite now has the wrong notes on B. Silent data corruption.

Why this is data loss, not just a UI glitch useEvent().updateEvent writes through IPC to better-sqlite3. There is no “are these notes for this event id?” check on blur. Whatever is in the box becomes the stored internalNotes for the loaded event.

4. Bug B — wipe while loading (high risk)

1

Open an event that already has notes

useEvent() starts fetching. For a moment eventDetails is undefined.

2

Card mounts empty

Parent passes eventDetails?.internalNotes ?? "" → defaultValue="". Textarea mounts blank.

3

Fetch completes

Prop becomes the real notes string — but uncontrolled textarea keeps showing empty unless something remounts it.

4

Accidental blur

Click into the empty box, click away → blur saves "" → existing notes wiped from the DB.

5. Why Client Details looks fine but Notes don’t

ClientDetailsCard renders {client.name} etc. from props on every render — pure display. Notes use a form control that caches its own state in the DOM. Same parent, two different React patterns, inconsistent sync.

6. “But controlled state adds another source of truth” — does it?

The objection: DB → React Query cache → React state → UI feels like four places holding the same value, all needing to stay in sync. So the React state layer was removed. Here’s the catch:

You never removed the fourth copy An uncontrolled <textarea defaultValue> still stores the text — inside the DOM. You didn’t eliminate the state; you moved it somewhere React can’t see or update. That invisible copy is exactly what causes Bugs A and B. The choice was never “3 layers vs 4 layers.” It’s “who owns the 4th layer: React, or the browser behind React’s back?”

The way out is to stop thinking in layers and think in roles. There are only ever two meaningful states for a field:

Saved state

What’s committed. Owned by React Query (the DB is just its persistence; the query cache is its in-app representative). You already treat this as the source of truth — keep that.

Draft state

What the user has typed but not saved yet. This state is unavoidable — it exists the moment someone types. It can live in React state (visible, controllable) or in the DOM (invisible, buggy). It is not a competing copy of saved state; it’s a different thing.

DB and UI drop out of the mental model: the DB is just where saved state persists, and the UI is just a projection of whichever state currently owns the field. Two owners, not four.

7. Who owns what, when

The “keep four things in sync” pain came from imagining the draft must always mirror the cache. It must not. The draft is seeded once, diverges freely while the user types, and is thrown away after save (the refetch brings back the authoritative value). There is no ongoing two-way sync to manage — just two one-way handoffs: seed on entry, commit on save.

8. Recipe A — single onBlur field (Internal Notes)

Three ingredients: a loading gate, an entity-keyed seed, and a no-op guard.

// OverviewWorkspaceSection.tsx — gate on load, key by entity
const { data: eventDetails, isLoading, updateEvent } = useEvent()

if (isLoading || !eventDetails) return <OverviewSkeleton />   // kills Bug B

<InternalNotesCard
  key={eventDetails.id}                       // new event = fresh card (kills Bug A)
  savedValue={eventDetails.internalNotes ?? ""}
  onSave={(value) => updateEvent({ internalNotes: value })}
/>
// InternalNotesCard.tsx — controlled draft, seeded once
const InternalNotesCard = ({ savedValue, onSave }) => {
  const [draft, setDraft] = useState(savedValue)  // seed happens at mount — key guarantees
                                                 // a fresh mount per event, so no useEffect needed
  return (
    <textarea
      value={draft}
      onChange={(e) => setDraft(e.target.value)}
      onBlur={() => {
        if (draft === savedValue) return        // no-op guard: focus+blur writes nothing
        onSave(draft)
      }}
    />
  )
}
  • Loading gate — the card can’t mount with an empty seed, so blur can never persist a false "".
  • key={eventId} — this is the trick that removes the sync wiring. Changing events unmounts the old card and mounts a fresh one, so useState(savedValue) re-seeds naturally. No useEffect, no “when do I re-sync?” question.
  • No-op guard — clicking in and out writes nothing; only real edits hit the DB.
  • After onSave, your existing useEvent flow (optimistic update → invalidate → refetch) takes over. The draft doesn’t need to hear back — the next mount re-seeds from the refetched value.
Why this isn’t the messy version The draft never listens to the query after mount. There is no effect syncing cache → state. Seeding is handled entirely by mount/unmount via key, and commit is one function call. Two handoffs, zero ongoing sync.

9. Recipe B — a whole form (you already built this)

EditEventSidebarForm.tsx already follows the draft pattern: one formValues draft seeded from the event, controlled fields, an explicit Save that commits everything at once, and React Query refetching afterwards. 

// EditEventSidebarForm.tsx — the shape you already have
const [formValues, setFormValues] = useState(createFormValuesFromEvent(event))

useEffect(() => {
  setFormValues(createFormValuesFromEvent(event))
}, [event])   // ← one refinement needed here, see below

<EventFormFields values={formValues} onChange={...} />
<button onClick={handleSave}>Save</button>   // draft → onSave(updates) → refetch
The one refinement: re-seed on identity, not on data Depending on [event] means any refetch that returns a new object (same data, new reference) resets the form and discards in-progress typing. Depend on [event?.id] instead — re-seed only when you’re editing a different event. Or skip the effect entirely and put key={event.id} on the form where it’s rendered, same as Recipe A.

Form vs single field — same model, different commit trigger

Whole form

  • One draft object for all fields
  • Commit on explicit Save click
  • Cancel = throw the draft away, nothing written
  • Good when fields relate to each other (dates, guest counts)

Single onBlur field

  • One draft string
  • Commit on blur (with a no-op guard)
  • No cancel button — blur without changes is the cancel
  • Good for independent long-text fields like notes

10. The checklist

  • Gate on load — never render an editable field before its saved value exists.
  • Key by entity — key={entityId} on the editable card/form so switching entities re-seeds by remount. This replaces sync effects.
  • Controlled inputs — value + onChange into draft state. Never defaultValue for DB-backed fields.
  • Seed once, diverge freely — no continuous cache → draft mirroring, ever.
  • Guard the commit — skip the write if draft equals saved value.
  • Let React Query close the loop — commit fires the mutation; invalidate/refetch restores query ownership. The draft never needs to “hear back.”
Mental model to keep Saved state belongs to React Query. Draft state belongs to the component that’s editing, seeded once per entity via key. The DB persists; the UI projects. Two owners, two one-way handoffs — not four synced copies.
